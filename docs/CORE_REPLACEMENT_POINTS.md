# CORE function-calling replacement points

Step 3 of the Week 1 plan, inspected 17 September 2026 at CORE baseline
`9c600a40afa6f7ad392bc9fe18931c0a28dfcdfe`.
Source counterpart: [FarmAgent source map](FARMAGENT_FUNCTION_CALLING_TRACE.md).
This document identifies the integration boundary. No implementation has been
replaced and no model or scoring experiment has been run.

## One existing task, end to end

Example: `computations_1`, "Add 15 and 7, then multiply the result by 3."

1. `run_experiments.py` selects hardcoded `ModelType` values and calls
   `baseline_agent.main()`. It then invokes a separate BFCL dataset runner.
2. `baseline_agent.py` constructs 14 world instances at module import. It loads
   `all_worlds_dataset.json`, indexes records by `prompt_id`, iterates the world
   prompt lists, and takes the user prompt text from the matching dataset record.
3. `worlds/computations.py` supplies the initial calculation history, methods,
   domain instructions, prompt IDs, and expected sequences. Tool definitions are
   generated by `World._get_tool_definitions()` using `llm_tool`.
4. The runner resets state and attempts task setup, then creates function-selection
   and completion-decision prompts and agents. Both agent classes construct a
   `Model` wrapper, whose initialization loads a Hugging Face tokenizer/model.
5. `FunctionAgent.get_next_function()` asks for text containing a fenced JSON
   object and extracts a function name and arguments using regex and JSON repair.
   This is text generation with a requested call format, not the native tool-call
   message interface used by FarmAgent.
6. The runner executes `getattr(world, name)(**arguments)`. On success it stores
   a `FunctionCalled`, refreshes the world-state text in both prompts, and asks
   `DecisionAgent.decide()` whether the task is finished. It repeats if not.
7. The runner saves result records including `world`, `prompt_id`, `prompt`,
   `functions_called`, parser/error counters, generated tokens, and final state.
   `functions_called` is a Python dataclass-representation string, not a JSON
   array of calls. There is no evaluation invocation in this runner.
8. Separately, `evaluate.py` loads dataset DFA/alphabet information and parses the
   saved call string. It maps names/arguments to symbols and passes the sequence
   to `core.evaluate()`. For this example, the intended calls are
   `add_numbers(a=15,b=7)` then `multiply_numbers(a=22,b=3)`, mapping to `A,C`.
   This is the expected path, not a reproduced run or verified score.

Suggested organization for step 4: put the adapted source in a distinct
`function_calling/` package inside CORE. This avoids a collision between the
existing `agents.py` module and a new package named `agents`, and preserves the
old imports used by `bfcl_agent.py`. Exact file layout remains an implementation
choice. The later runner integration should make the new path discoverable.

## Contracts to preserve or make explicit

- **Task identity:** join by `prompt_id`, preserve the dataset's selected prompt,
  and do not expose its DFA, alphabet, or expected solutions to the model.
- **Tool meaning:** reuse CORE's existing callable methods and their effects.
  Preserve canonical names for evaluation, even if model-facing names use
  FarmAgent's `WorldName__method` prefix. Use an explicit mapping.
- **Observation access:** old CORE gives the model current world state after
  successful actions, not just tool return values. Preserve that access in the
  initial prompt and subsequent observations; otherwise the port also changes
  what information the agent can see. Keep protocol-required tool replies valid.
- **Termination:** no tool call means the agent chose to stop, not that it passed
  the task. Limits and errors must have separate recorded stop reasons.
- **Execution policy:** record single/multiple-tool response handling, argument
  coercion, prompts, and generation settings. Do not claim the new path is a
  prompt-only comparison: it also changes completion logic and model interface.
- **Evidence:** preserve requested and executed arguments, failed attempts, and
  results. An error return and a raised exception are different events. Deep-copy
  mutable arguments/results/state when recording snapshots.
- **Evaluation:** keep the original metric definitions separate from runtime
  error counters. A completed run and a parseable trace are not a metric score.

## Existing CORE issues encountered at these boundaries

These are source-inspection findings, not migration-created defects. Necessary
execution fixes should be documented independently of the imported FarmAgent
fixes, because they can affect comparison with historical runs.

1. **Setup key mismatch:** `baseline_agent.py:83` reads `prompt['functions']`
   via `.get()`, while world definitions use `setup_functions`. Nonempty setup
   actions are therefore ignored by that code path. For example, `automation_2`
   intends to unlock the door before asking the agent to lock it and arm the
   alarm. Some setup entries also have nested lists, so setup needs validation;
   simply changing the key is not sufficient across all tasks. Do not carry
   unrestricted `eval()` into a new setup interface.
2. **Shallow reset:** `World.reset_world_state()` copies only the outer dictionary.
   Nested lists/dictionaries remain shared with `_init_world_state`. Computations
   appends to just such a list, allowing task state to persist across resets.
   Fresh world instances and independent snapshots are needed for isolated runs.
3. **Legacy output coupling:** `FunctionCalled` is defined in `agents.py`, which
   imports `model.py` and the GPU stack. Do not import all this solely to format
   new traces. `database` and result objects can also retain mutable references
   until the final results file is written.
4. **Counters are protocol-specific:** old `mistakes` fields count formatting,
   parsing, and dispatch failures. They are not CORE's five paper metrics.
   Do not equate new tool-protocol errors with identical historical counters
   without an explicit definition.
5. **Dataset regeneration is a separate concern:** `build_json_dataset.py`
   currently maps `computations` to a class called `Maths`, whereas the current
   world class is `Computations`. Use and validate the supplied dataset for the
   port rather than casually regenerating it. Old saved result records inspected
   also lack `prompt_id`, unlike the current runner's output definition.

## Evaluator limitations to keep separate from the port

`evaluate.py` is an experimental entry point, not a demonstrated complete batch
implementation of the paper's five metrics:

- Its command-line example selects fixed dataset/result indices rather than
  joining the supplied files by task ID.
- Its legacy parser rewrites quotes and strips square brackets, which is fragile
  for nested/list-valued arguments and responses. New traces should use structured
  data; legacy support must be exercised against representative old records.
- `fc2symbol()` indexes by function name, so unknown names can raise `KeyError`.
  Known names that match no symbol are skipped by `evaluate_world()`. Recording
  failed attempts faithfully does not by itself make this evaluator score them
  correctly. Their treatment needs an explicit evaluation decision.
- `core.py` has module-global path caches initialized for its example DFA;
  `convert_dfa()` mutates supplied nodes. Repeated-task evaluation requires checks
  before trusting scores. `core_2.py` provides a separate experimental scoring
  route and is not what `evaluate_world()` calls.

For step 6, distinguish input compatibility from metric correctness. Verify
canonical name/argument mapping first, then validate scoring with known traces.
Do not silently rewrite metric behavior as part of the function-calling port or
advertise scores as paper-faithful before that validation.

address its documented defects, and expose a clean callable interface. Step 5
connects the first existing CORE world; step 6 connects evaluation; later steps
verify additional worlds and make the new runner the normal entry point.

during the initial runtime port. Preserve legacy agents/model files because the
BFCL runner still imports them. Migrating that runner should be a deliberate
follow-up rather than an accidental break caused by deleting shared code.
