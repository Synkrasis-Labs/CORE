# CORE → ARE smoke test

The first opt-in migration slice runs the original `computations_1`
task in ARE, using CORE's existing arithmetic implementation. ARE owns the app,
scenario, event ordering, and tool log. CORE's unchanged saved-trace evaluator
scores the resulting path. The driver is an ARE oracle script, **not an LLM**.
The checkpoint below adds a second task, `crud_2`, with setup and stateful reads/writes.

## Run

From this checkout:

```sh
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements-are.txt
.venv/bin/python -m are_integration.smoke --output /tmp/core-are-smoke.json
```

The command succeeds only if ARE executes both actions in order, returns 22 and
66, reaches the expected app state, exports both calls with arguments, and the
legacy CORE scorer returns 1.0. The evidence file includes the full converted
run artifact, evaluator result, and individual check results. No provider key is
needed. The scorer is the existing legacy path scorer; this does not reproduce
all five CORE paper metrics or establish LLM task success.

To make the scenario discoverable by ARE's CLI, install this checkout in editable
mode from the repository root after installing the dependencies:

```sh
.venv/bin/python -m pip install -e .
.venv/bin/are-run -s core_computations_1 -o
```

The oracle CLI command checks ARE registration and scenario execution. The
`are_integration.smoke` command above additionally checks CORE trace conversion
and scoring.

## One live ARE agent (paid)

Put `OPENAI_API_KEY="..."` in this checkout's ignored `.env`, or export it in
the shell. Then run from the repository root:

```sh
.venv/bin/python -m are_integration.live
```

This uses ARE's default text-action agent and OpenAI `gpt-4.1-nano`. The dedicated
runner makes at most six model requests, caps each response at 256 tokens, sets a
30-second request timeout, and disables SDK retries. Use `--max-requests`,
`--max-output-tokens`, or `--model` to change those limits. It runs one ARE user
turn. The output path printed at the end contains `run.json` with the actual
agent tool path, CORE legacy score, validation, usage, and limits, plus ARE's raw
trace JSON. A failed task or an unscored trace is saved as evidence, not hidden.

The first paid run on 30 September 2026 used `gpt-4.1-nano` and made three model
requests. The agent called `add_numbers(15, 7)` and then
`multiply_numbers(22, 3)`. ARE validated the final calculation state (66), and
CORE's legacy path scorer returned 1.0. The agent's final user-message call had
an invalid argument type, so no final reply was delivered. The original CLI field `are_success` reported
the computation-state validation; it does not establish successful reply delivery
or reproduce all five CORE paper metrics. The local raw trace and converted run
artifact are saved under `runs/are/computations_1/` and ignored by Git.

ARE's `--provider openai` in version 1.2.0 selects a Hugging Face client; this
runner instead provides ARE's agent with a directly configured OpenAI engine.

## Where CORE plugs into ARE

| CORE | ARE | Owner in this slice |
|---|---|---|
| `Computations` methods and world state | `CoreComputationsApp` tools and state | `are_integration/computations.py` |
| `computations_1` prompt and reference calls | `CoreComputationsOne` user event and oracle events | `are_integration/computations.py` |
| Tool call sequence | ARE `Environment.event_log` | `are_integration/smoke.py` and `are_integration/live.py` |
| CRUD methods, setup, and task `crud_2` | `CoreCRUDApp` and `CoreCRUDTwo` | `are_integration/crud.py` |
| DFA alphabet and legacy path score | Existing `function_calling.evaluation` | Unchanged |

The adapter reads only ARE **agent** events from the CORE app. It retains the
actual call order, arguments, results, error status, ARE event ID, and event
time. User and environment events are kept out of CORE's agent path. The oracle
run is a reference execution fixture. The live runner uses the same adapter on
events generated by an ARE agent.

## Completion reporting and parity checkpoint (1 October 2026)

The bounded runner now prints `are_state_success`, `reply_delivered`, and
`core_score`/`core_status` separately. It exits nonzero if state validation fails,
a runner exception occurs, or no reply reaches ARE's user-interface state.
A delivered reply is not a check of its correctness or model completion. ARE
can deliver an automatic stop message after exhausting the request budget.
The legacy path score is independent of this exit status, which can be zero
when state validation passes and only the automatic stop message is delivered. An unscored CRUD path can still validate and
have a delivered reply.

`run.json` additionally preserves ARE reactor `agent_logs`, parsed
`tool_attempts`, and `reply_delivery` with actual messages. Parsed attempts are
matched to CompletedEvents in order. Attempts without an event have status
`not_observed`, their original arguments, and executor errors where available.
This status does not prove execution never began. CORE-app attempts absent from
the event log remain in the converted workflow and prevent a partial path from
being scored. UI attempts stay outside the CORE world path. Malformed actions
that cannot be parsed remain in agent logs rather than invented tool calls.

The pasted live log identifies the final-message failure precisely: the model
passed `content={"type":"string","description":"The final result of the calculation is 66."}`
instead of a string. The offline agent replay covers that exact payload and a
valid `content="66"`, preserving the invalid attempt without coercion. Existing
paid-run artifacts have not been rewritten. No new paid run was made for this
checkpoint.

Run the scripted parity gate with no model or provider:

```sh
.venv/bin/python -m are_integration.parity --output /tmp/core-are-parity.json
```

It compares original CORE arithmetic (inherited without changes through the
existing FunctionCallingComputations wrapper) against real registered ARE app
calls: names, arguments, results/errors, intermediate and final state, and the
unchanged evaluator output. The reference scores 1.0 and reversed order scores
approximately 0.3333 in both. An extra subtraction, a failed addition, and an
extra divide-by-zero call are retained; the legacy evaluator leaves them
unscored. Division by zero returns None successfully, not an execution error.
This scripted gate tests runtime/trace parity, not relative model performance.

## Stateful slice: CRUD

`core_crud_2` migrates one setup-dependent source task. Its ENV setup creates
Alice before the user request. The oracle then lists users, updates her email,
and verifies it. All five original CRUD domain methods are exposed, with reads
marked READ and mutations WRITE; legacy helper methods are not exposed.

```sh
.venv/bin/python -m are_integration.crud_smoke --output /tmp/core-are-crud.json
.venv/bin/are-run -s core_crud_2 -o
.venv/bin/python -m unittest tests.test_are_live tests.test_are_trace tests.test_are_parity tests.test_are_crud tests.test_evaluation -q
```

These commands are offline. The CRUD oracle and a mocked text-action agent both
validate the expected state. Setup stays out of the agent path; list/verify reads
stay in it. The complete path remains **unscored** because the unchanged mapper
cannot map zero-argument `list_users()`. It is not scored after dropping the read.

The ARE CRUD wrapper freezes `list_users` results with a deep copy: the original
method returns references to live user dictionaries, which would let later
updates rewrite the earlier event's observation. Returned values and world
mutations are otherwise inherited from the source. Checks cover all five domain
methods, False results without exceptions, frozen read observations, state
snapshot/load isolation, app reset, and fresh scenario instances. ARE's
`initialize()` is idempotent; reuse does not reset a scenario.

The bounded runner accepts `--scenario core_crud_2`. Live checks for this task
are summarized below; final answer delivery remains unresolved.
Do not treat this as migration of all CRUD tasks. Source `crud_3` reference email
typos and duplicated updates remain untouched, along with other documented
scenario defects. Original runner, worlds, mapper, and scorer are unchanged.

The ARE-only virtual environment does not install the separate shared-runner
`llm-tool` dependency from `requirements-experiments.txt`; full test discovery
therefore has three Navigation-related failures. All 22 focused migration/evaluator checks and both ARE oracle scenarios pass.
Full discovery ran 65 tests: 62 passed, with one failure and two errors caused
by the missing Navigation dependency.

## CRUD live checkpoint (1 October 2026, Berlin time)

All model runs used the same CRUD task/tools, six model requests maximum, a
30-second request timeout, and zero SDK retries. They are individual exploratory
runs, not a controlled comparison or a success-rate estimate.

| Model | Completion-token cap per request | Requests | ARE state validation | Model final reply |
|---|---:|---:|---|---|
| GPT-4.1 nano | 256 | 6 | Passed | Plain text rejected; automatic stop message delivered |
| GPT-4o mini | 256 | 4 | Passed | Dictionary supplied for string content; no message delivered |
| GPT-5 nano | 256 | 6 | Failed; no CRUD calls | Empty text; automatic stop message delivered |
| GPT-5 nano | 512 | 6 | Failed; no CRUD calls | Empty text; automatic stop message delivered |
| GPT-5 nano | No client cap | 6 | Passed | Plain text rejected; automatic stop message delivered |

The uncapped GPT-5 nano run listed users, updated Alice's email, verified it,
and listed users again. Its first action required 593 completion tokens,
including 512 reasoning tokens. Later requests used 640–2240 reasoning tokens.
All six responses had finish reason `stop`. This strongly supports the small
completion-token cap as the cause of the earlier empty outputs, while reply
formatting remains a separate issue. All CRUD paths are unscored: successful
paths include the unmappable zero-argument read, and unsuccessful runs have an
empty world-tool path. No calls were dropped to manufacture a score.

The engine now saves `reasoning_tokens` and `finish_reason` alongside usage.
`run_live(max_output_tokens=None)` omits `max_completion_tokens` from the API
request and records a null cap. Provider/model limits still apply. This Python
API option does not change the CLI default of 256 or its integer argument.
The six-request limit and timeout remain active. Keys were passed in memory
from the original CORE checkout for these runs, without copying or committing
credentials; the standard CLI still loads this checkout's ignored `.env` first.

   Review recovery behavior and prompting before authorizing another paid run.

   isolation. Expand to additional CRUD tasks, documenting source defects separately.
4. **Coverage:** Create a world/task inventory and move through the 13 worlds in
   this checkout. Track Farm/Arm separately because their paper implementations
   are absent here. Repair known source defects as explicit, reviewed changes.
5. **Paper metrics and comparison:** Reproduce all five CORE metrics from ARE
   traces, then compare ARE prompting and vanilla function calling on matched
   scenarios, tools, model versions, call limits, and seeds. Report task success
   separately from path scores.

For the broader experiment, ARE is the runtime and event source; CORE's DFA and
metrics remain the process evaluator. Gaia2's write-action verifier is a separate
evaluation signal and must not replace CORE's full-path scoring, which counts
read calls and harmful attempts as well.
